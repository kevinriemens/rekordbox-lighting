## 1. User Story

**As a** DJ using `rbxlight` to manage rekordbox lighting macros\
**I want** YAML exports of macros to show indented, readable XML instead of single-line payloads\
**So that** I can diff exported macros against rekordbox's own XML output and manually inspect macro structure without parsing a wall of text

## 2. Business Context & Value

The `rbxlight` CLI exports macros as YAML files containing raw `LightingEditModel` XML payloads. Currently, these payloads are compact single-line strings (as generated by the tool's serialization). Pioneer rekordbox itself writes 2-space-indented XML, making it difficult to diff exports against rekordbox's own data or to read macro structure by eye.

This is purely a **reading concern** — the bytes written to the database must remain unchanged. Indentation belongs at the export boundary, not in the serialization layer. This constraint keeps the story small and preserves the round-trip guarantee: macros generated before and after this change must produce identical database content.

## 3. Acceptance Criteria

* [ ] **Scenario 1: Indented XML in YAML export**
    * Given a macro with multiple fixture slots containing `LightingEditModel` XML
    * When the macro is exported to YAML
    * Then each XML payload in the `fixtures` mapping is indented with 2 spaces, matching rekordbox's format
    * And the XML remains valid and parseable

* [ ] **Scenario 2: Empty payload handling**
    * Given a macro with empty fixture slots (legitimate empty strings in the database)
    * When the macro is exported to YAML
    * Then empty payloads remain empty strings (not indented empty documents)
    * And the YAML export remains valid

* [ ] **Scenario 3: Corrupt or unparseable payload**
    * Given a macro with a payload that fails to parse (unexpected or corrupt data read from the database)
    * When the macro is exported to YAML
    * Then the raw string is emitted unchanged rather than raising an exception
    * And the export completes without crashing

* [ ] **Scenario 4: XML declaration preserved**
    * Given a valid `LightingEditModel` payload with an XML declaration
    * When the payload is indented for export
    * Then the declaration line (`<?xml version="1.0" encoding="UTF-8"?>`) survives intact at the top

* [ ] **Scenario 5: YAML validity with multi-line XML**
    * Given a macro exported to YAML with indented XML strings
    * When the YAML file is parsed by a standard YAML parser
    * Then it is valid YAML (multi-line block scalars are handled correctly)
    * And the XML can be extracted and parsed back to the same model

* [ ] **Scenario 6: Database write path unchanged**
    * Given a macro generated by the tool before this change
    * When the same macro is generated after this change
    * Then the bytes written to `macro_data.data` in the database are identical
    * And no existing macros in the database are reformatted

## 4. Technical Constraints

* **Export formatting**: Apply indentation at the export boundary only — specifically where YAML exports are generated. The serialization layer (`serialize()` in `lightingxml.py`) must remain unchanged; its output goes directly to the database and must be byte-identical before and after this change.

* **Indentation standard**: Use 2-space indentation to match rekordbox's own XML output, enabling direct diff comparison.

* **Lossless round-trip**: The indented XML must parse back to the same `LightingEditModel` without data loss. This requires confirming that the `LightingEditModel` format is attribute-only (no meaningful text content in elements). If any element carries text content, indentation would corrupt it — this must be verified and stated explicitly in the implementation.

* **Error handling**: Indentation must be defensive. If a payload fails to parse, emit the raw string unchanged rather than raising an exception, allowing exports to complete even with corrupt data.

* **Dependencies**: Use Python 3.12 stdlib only — specifically `xml.etree.ElementTree.indent()` if available, or equivalent stdlib mechanisms. No new external dependencies.

* **Empty payload handling**: Empty strings must remain empty strings, not become indented empty XML documents.

## 6. Scope & Context

### Load-bearing constraint

The user explicitly chose to indent **exports only**, not database writes. This decision is the reason the story is small. The rationale:

- The bytes in `macro_data.data` are the project's round-trip surface. Reformatting them would change every byte of every macro the tool has ever written, for zero functional gain.
- Future diffs against previously-written rows would become noisy exactly when they most need to be quiet.
- Indentation is a *reading* concern and belongs at the reading boundary, not in serialization.

### Existing code facts (verified)

- `src/rbxlight/lightingxml.py` owns serialization. `serialize(model: LightingEditModel | None) -> str` returns `'<?xml version="1.0" encoding="UTF-8"?>\n' + ET.tostring(...)` — compact single-line. `serialize(None) == ""`. This function has exactly three callers, all in `src/rbxlight/macros/generate.py`, and their output goes directly to `macro_data.data`. **These callers must not change.**

- `src/rbxlight/macros/yaml_io.py` contains `export_macro_yaml(conn, macro_id: int) -> str`, which emits a YAML mapping with `name`, `beats`, and a `fixtures` mapping of all 25 fixture slots, each holding the raw XML string from the database. **This is the human-reading boundary and the place indentation belongs.**

- Project invariants that must survive:
  - Exact round-trip: `parse(serialize(x)) == x`
  - Fixed section order: Brightness, Colour, Strobe, Position, Rotate, Gobo
  - Empty sections still emitted as self-closing tags
  - `generate.py` and `transform.py` are pure and never touch a database

### Sibling story relationship

A second refined story, `CLI_COMPLETENESS-macro-discovery-commands`, introduces `rbxlight macro show <id> --yaml` reusing `export_macro_yaml`. If that story lands first, it inherits indented XML for free once this one lands. Neither story blocks the other; note the relationship but do not create a hard dependency.

### Out of scope

- Changing what `serialize()` returns to its three `generate.py` callers
- Any change to the database write path, the 25-row invariant, or the safety/backup machinery
- Reformatting XML already stored in live databases
- Introducing an XML library dependency beyond stdlib

## 7. Test Impact Analysis

### Existing tests affected by this change

The test suite (577 tests, all passing) lives under `tests/`, mirroring `src/`. Tests build throwaway SQLite databases in `tmp_path` via `conftest.py`. Golden `LightingEditModel` payloads are captured in `tests/fixtures/`.

**Critical invariant**: Tests must never touch anything under `~/Library/Application Support/Pioneer/rekordbox6/` — not even a read.

Tests asserting the database write path (macros generated before and after this change produce identical `macro_data.data` bytes) are the most valuable. Existing tests that verify serialization round-trip (`parse(serialize(x)) == x`) must continue to pass without modification.

Tests that export macros to YAML and inspect the output will see indented XML after this change. These tests should be updated to expect indentation, but the underlying assertion — that the exported YAML is valid and the XML parses back to the same model — remains the same.

### Test modification policy

- [ ] Existing tests asserting database write behavior must not be modified (the bytes written must remain identical)
- [ ] Existing tests asserting serialization round-trip must not be modified
- [ ] Tests that inspect YAML export output may be updated to expect indented XML
- [ ] New tests should verify: (1) indented XML in exports, (2) empty payload handling, (3) corrupt payload fallback, (4) YAML validity with multi-line XML

### Existing files impacted

| File | Impact |
|------|--------|
| `src/rbxlight/lightingxml.py` | No change — `serialize()` output must remain byte-identical |
| `src/rbxlight/macros/generate.py` | No change — callers of `serialize()` must not be modified |
| `src/rbxlight/macros/yaml_io.py` | Indentation logic applied at export boundary; `export_macro_yaml()` output changes to include indented XML |
| `tests/` | Tests asserting database write behavior remain unchanged; tests inspecting YAML export output may be updated to expect indentation |
